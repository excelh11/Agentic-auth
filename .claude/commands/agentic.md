# Security/JWT 파이프라인 실행

요청: **$ARGUMENTS**

아래 4단계를 **순서대로** 진행한다. 각 단계가 끝나면 결과를 보여주고 **사용자 승인을 받은 뒤** 다음 단계로 넘어간다.

```
SPEC (무엇을?) → PLAN (어떻게?) → TASKS (어떤 순서로?) → IMPLEMENT (코드로 구현)
```

| 단계 | 담당 에이전트 | 산출물 | 어디에 남나 |
|---|---|---|---|
| 1. SPEC | `agentic-spec` | 요구사항 명세, 계약 영향 분석 | **`docs/1-SPEC.md` 에 직접 기록** |
| 2. PLAN | `agentic-plan` | 기술 선택, 설계 결정, 위험 요소 | 대화 (쓰기 권한 없음) |
| 3. TASKS | `agentic-tasks` | 의존성 순서대로 쪼갠 작업 목록 | 대화 (요청 시 `docs/4-TASKS.md`) |
| 4. IMPLEMENT | `agentic-impl` | 코드 + 테스트 + 검증 결과 | **코드 + `docs/` 동기화** |

## 단계 간 인계 — 이게 빠지면 파이프라인이 끊긴다

**에이전트는 서로의 대화를 볼 수 없다.** 각자 자기 컨텍스트에서만 돈다.
그러므로 다음 단계를 호출할 때 **앞 단계의 산출물을 프롬프트에 직접 담아 넘겨야 한다.**

- **SPEC → PLAN** : 확정된 요구사항, 계약 영향, **미확정으로 남긴 열린 질문**을 그대로 전달한다.
- **PLAN → TASKS** : 기술 선택과 그 근거, **승인받은 항목**(신규 의존성·스키마 변경 등),
  그리고 PLAN이 찾아낸 **위험 지점**을 전달한다.
- **TASKS → IMPLEMENT** : 작업 목록 전체, **원자적으로 묶어야 하는 단위**,
  각 작업의 **검증 명령**, **멈춰야 하는 조건**을 전달한다.
- 사용자가 중간에 내린 결정(승인·거부·선택)은 **매 단계마다 다시 실어 보낸다.**
  앞에서 합의한 것을 다음 에이전트는 모른다.

## 진행 규칙

0. **시작 전 [`docs/0-RULES.md`](../../docs/0-RULES.md) 를 읽는다.** 이 저장소에서 실제로 사고가 났던
   항목들이다 — 조용히 실패하는 것들, 이 환경의 함정(`sed`·인코딩), 검증 규칙, 되돌릴 수 없는 것들.
1. **한 번에 한 단계만.** 4단계를 몰아서 실행하지 않는다.
2. SPEC 단계에서 **기존 명세(F1~F13)가 깨지는 것이 발견되면 즉시 멈추고** 사용자에게 알린다.
3. PLAN 단계에서 **신규 의존성이 필요하면 승인을 받기 전까지** TASKS로 넘어가지 않는다.
4. IMPLEMENT 단계는 **TASKS 목록 없이 시작하지 않는다.**
5. 요청이 명백한 단순 수정(오타, 상수값 하나, 로그 문구)이면 SPEC/PLAN을 2~3줄로 압축하고 바로 IMPLEMENT로 간다.

## 마무리

IMPLEMENT 완료 후 반드시 아래를 보고한다.

- 변경 파일 목록
- `gradlew compileJava` / `gradlew test` 실행 결과 (실패는 원문 그대로)
- `docs/3-TEST.md` §6 회귀 체크리스트 중 확인한 항목
- 프론트엔드에 영향 가는 계약 변경 (없으면 "없음")
- 명세가 바뀌었다면 `docs/1-SPEC.md` 갱신 여부
